# Spec-Driven Development (SDD)

> Unlike `architecture.md`/`conventions.md`/`verification.md`, this file has no TODOs to fill in — the
> EARS format, lifecycle, and traceability convention below are harness mechanics, identical across
> every project that opts a feature into SDD. Nothing here is project-specific.

## What this is

A feature can require a **human-approved spec** before any code is written. This is **opt-in per
feature** (`sdd=1`) — every feature that doesn't opt in works exactly as it always has: `pending →
claim → in_progress → done`.

Opt a feature in with any of:
- `scripts/harness.sh add-feature --name <slug> --title <t> --sdd`
- a `features.seed.json` item with `"sdd": true`
- a Notion database checkbox property named `SDD` (if Notion intake is configured — see `AGENTS.md` §0)

## Lifecycle

```
pending ──claim-spec──> spec_drafting ──mark-spec-ready──> spec_ready
                                                                │
                                                  (human reviews the 3 files,
                                                   approves in conversation)
                                                                │
                                                                ▼
                                                          approve-spec
                                                                │
                                                                ▼
                                                    claim ──> in_progress ──log-out──> done
```

- **`scripts/harness.sh claim-spec [TARGET]`** — a `spec_author` subagent claims a `pending, sdd=1`
  feature, opening a session (mirrors `claim`).
- **`scripts/harness.sh mark-spec-ready`** — closes that session once
  `specs/<name>/{requirements.md,design.md,tasks.md}` all exist on disk; records requirement/task
  counts; moves the feature to `spec_ready`.
- **Human approval** — the user reads the 3 files and approves, in conversation. The leader then runs
  **`scripts/harness.sh approve-spec <target> --by <name>`** — this is the actual DB-recorded gate.
  Nothing mechanical can verify a human's judgment, but this at least proves *someone* explicitly
  recorded approval, with a timestamp and a name, rather than the leader silently skipping the step.
- **`scripts/harness.sh claim [TARGET]`** — for an `sdd=1` feature, only succeeds once its spec is
  recorded `approved` (and the 3 files are still present on disk). From here the feature proceeds
  exactly like any non-SDD one: `implementer` then `reviewer`, then `log-out`.

## File layout

```
specs/<name>/
├── requirements.md   # WHAT is needed (EARS notation)
├── design.md         # HOW it will be built (technical decisions)
└── tasks.md          # Concrete, ordered steps to implement
```

`<name>` must match the feature's `name` field exactly (`scripts/harness.sh status`) — that's how
`claim`, `mark-spec-ready`, `init.sh`, and the reviewer all locate it. **`specs/` is git-tracked, like
`src/`/`tests/`** — never gitignored, never regenerated by `scripts/snapshot.sh` (unlike `state/`,
which is a disposable, wholesale-regenerated view of the database, spec content here is the actual
source material).

## Requirement format: EARS

Every requirement in `requirements.md` gets a stable id (`R1`, `R2`, ...) and follows one of these five
patterns:

| Pattern | Template |
|---|---|
| Ubiquitous | `The system SHALL <action>.` |
| Event | `WHEN <trigger>, the system SHALL <action>.` |
| State | `WHILE <state>, the system SHALL <action>.` |
| Optional | `WHERE <optional feature>, the system SHALL <action>.` |
| Unwanted | `IF <unwanted event> THEN the system SHALL <action>.` |

Hard rules:
- Each requirement has exactly one verifiable `SHALL` clause — never mix two behaviors into one `R<n>`;
  split them.
- No soft/unverifiable verbs ("should probably", "handle appropriately", "supports"). If it can't be
  turned into a pass/fail test, it isn't a requirement yet — sharpen it or move it to `design.md` as a
  note instead.

Example:

```markdown
## R1
WHEN the user runs `export`, the system SHALL write a JSON file to the given path.

## R2
IF the output path already exists THEN the system SHALL fail with a non-zero exit code and SHALL NOT
overwrite the existing file.
```

## `design.md`

Files to touch, new signatures, exceptions/error paths, and **at least one discarded alternative with a
stated reason it was rejected**. Reference `docs/architecture.md`/`docs/conventions.md` rather than
re-deriving this project's conventions from scratch — `design.md` should only need to explain choices
made *within* those boundaries, not restate them.

## `tasks.md`

Ordered checkboxes (`T1`, `T2`, ...), each tagged with the `R<n>` id(s) it covers:

```markdown
- [ ] T1 (R1) Add `cmd_export` to the CLI.
- [ ] T2 (R2) Add the existing-file check.
- [ ] T3 (R1) Add `test_export_default`.
- [ ] T4 (R2) Add `test_export_existing_path`.
```

The `implementer` checks these off in order as it works; the `reviewer` rejects the feature if any are
left `[ ]` without a documented justification in `progress/impl_<feature>.md`.

## Traceability

Every `R<n>` must be covered by **at least one concrete, currently-passing test**. The `implementer`
documents this mapping in `progress/impl_<feature>.md`:

```markdown
## Traceability
- R1 → `test_export_default`
- R2 → `test_export_existing_path`
```

The `reviewer` does not trust this claim — it independently confirms each named test exists and
actually exercises the requirement it's mapped to (see `.claude/agents/reviewer.md` / `.codex/agents/
reviewer.toml`, step 4b), and checks the same `R<n>` coverage as part of `CHECKPOINTS.md`'s C6 group.
